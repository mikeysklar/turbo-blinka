## #192, the one in review

https://github.com/adafruit/Adafruit_Blinka_Displayio/pull/192

Branch `vectorio-travel-box`, one commit `93a9f41`, `vectorio/_vectorshape.py` only,
+18/-10, sitting directly on `92545ce`. black clean, pylint 10.00/10 across
`vectorio displayio busdisplay bitmaptools`.

The change: `_consume_dirty_areas` unioned the new position as well as the old, so
the area to clean up always contained the current area, the choice further down
between one combined rectangle and two separate ones could only pick the combined
one, and the `else` branch was unreachable. CircuitPython unions only the old
position, `VectorShape.c:204`. Three parts:

1. the union takes only the position being left behind
2. `_finish_refresh` empties that area, `VectorShape.c:483`, needed now the union reads it back
3. `compute_overlap`'s size is used only when it reports an overlap, since it leaves
   `y1` and `y2` alone when the x ranges miss

Measured on panels, three shapes bouncing 12 s, SPI at 24 MHz:

| board | step | before | after |
|---|---|---|---|
| Pi 5, HX8357 480x320 | 220 px | 3.23 fps | 6.77 fps |
| Pi 5, HX8357 480x320 | 6 px | 8.08 fps | 8.12 fps |
| Zero 2 W, ILI9341 320x240 | 160 px | 1.43 fps | 2.25 fps |
| Zero 2 W, ILI9341 320x240 | 6 px | 2.15 fps | 2.22 fps |

The precondition matters and the PR says so: a step smaller than the shape leaves the
old and new boxes overlapping, so one combined area is still cheaper and nothing
changes. Drawing time barely moves, 8.40 to 8.14 ms headless. The gain is transfer,
which halves exactly, 115,211 to 57,622 bytes per frame for a 120 px shape.

## Dropped, with the reason

The `_ondisk_column_span` follow-up PR (key the span per grid row, replace both scans
with a boundary walk). Measurement killed it: 1 px of a 4000 px row reads 1166 bytes
at 8 bit and 150 at 24 bit, identical before and after the span fix, so the clipping
already works for an ordinary bitmap. The only case that over-reads is a sheet whose
visible tiles sit far apart horizontally on different grid rows, since the span is a
single enclosing range across rows. The setup scan runs once per fill, ahead of a
per-pixel fill of the same width, so it is noise against the work it precedes. The
code is correct either way, verified across 20 sprite sheet layouts on both boards.

## Methodology worth not relearning

The framebuffer oracle is required whenever a change deliberately alters the bytes
sent. Hook `display._core.set_region_to_update` and `display._send_pixels`, replay
every window and blob into a framebuffer, then compare against the same scene drawn
with `_core.full_refresh = True`. A hash of the bytes on the wire is useless there,
because sending different bytes is the whole point of the change.

Attach the recorder before the first refresh, then subtract the first draw from the
pixel count, or "no change at all" falsely reports stale.

GitHub diffs a PR from its merge base, so a stale base does not show reversions.
`git diff upstream/main..branch` compares tips and misleads.

PR order is forced for anything touching `_tilegrid.py`, and each merge needs a rebase
of the rest.
